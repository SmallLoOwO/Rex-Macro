# REENTRY 鏡頭遠近支援（zoom 指令＋絕對歸位）設計

日期：2026-07-12
狀態：設計定案，待實作計畫
前置：`2026-07-12-remote-reentry-design.md`（遠端回礦主設計）、`2026-07-11-pitch-sweep-design.md`（「夾限飽和→回拉固定量」絕對歸位手法與 `pitch_eaten_*` 獨立門檻先例）

## 問題

遠端回礦的八方位快照在**預設鏡頭距離**下拍攝；部分重生點離地表面板較遠，預設距離看不到面板，需要拉遠鏡頭才拍得到。網格換算本身不受影響（粗格/細格換算的是當下截圖的螢幕像素座標），受影響的是三件事：

1. **可見範圍**：面板不在快照裡，使用者無從指位。
2. **鏡頭狀態外洩**：zoom 是持續存在的鏡頭狀態，拉遠後不還原，回 MINING 整套視覺（追蹤框尺寸、採集八方位掃描視野）都在非校準距離下跑——與 H026 FOV 縮放同族風險。
3. **落盤資料尺度**：同一面板在不同 zoom 下渲染大小差很多，ground truth 不記 zoom，未來模板庫尺度分佈會亂。

## 已確認的事實與決策（2026-07-12 問答）

| 問題 | 決策/事實 |
|---|---|
| 使用頻率 | **只有部分重生點不夠遠** → 按需指令（同 `走` 的地位），不改開場鏈 |
| 操作方式 | I（拉近）/ O（拉遠）鍵，離散步進、可數、可驗證（與 `,`/`.` 同族）；滾輪也可但不採用 |
| 挖礦鏡頭距離 | **中間距離**（影響採集八方位掃描視野）→ 不在夾限上，還原是真問題、不能馬虎 |
| 還原策略 | **絕對基準**（方案 B）：拉近到第一人稱夾限飽和 → O 回拉校準 K 步。反向記帳（方案 A）被否決：I/O 步進對稱性未驗證＋送鍵被吃會讓記帳脫鉤、誤差直接漏進 MINING |
| 歸位時機 | **碰過才歸位**：episode 用過 `遠`/`近` 才執行，掛在離開 REENTRY 的所有出口（同 `_pitch_restore_if_touched` 語意） |

## 第 1 節：指令（`reentry_remote.parse_reply` 新增兩個 kind）

| 回覆 | 動作 |
|---|---|
| `遠 [n]` | 按 O n 次拉遠（n 省略＝`reentry_zoom_step_default`，上限 `reentry_zoom_max_steps` 防手滑）→ 其餘方位快照視為過期（同 `走`）→ 重拍當前面向＋粗網格回傳單張 |
| `近 [n]` | 同上但按 I 拉近（拉遠過頭往回收） |

- 只在 `awaiting_cmd` 收——等細格時鏡頭一動放大圖必然作廢，回時機提示。
- **`zoom_reset_pullback_steps=0`（未校準）＝整組指令停用**，回「zoom 未校準」提示不動作——還原不了就不許動，同 `sweep_pitch_enabled` 保險模式。
- 英文別名 `far`/`near` 比照既有詞彙表雙語慣例。

## 第 2 節：執行與驗證（`Bot._rr_zoom_cam`，I/O 在 main）

`_focus_roblox` → 逐步送 O/I，每步前後截幀比對「被吃」（zoom 一步整個場景縮放、幀差大）→ 被吃重送（上限同 rotation 模式）。

- 門檻用**獨立的 `zoom_eaten_*`**，不共用旋轉門檻——俯仰事故已證明地表粒子特效會讓「沒動的畫面」frac 也有 0.022~0.045、門檻必須分家；初值抄 `pitch_eaten_*`（mean 8.0 / frac 0.15）再實機校準。
- 淨步數記 `ctx.net_zoom`（+＝遠）；`重骰` 不清（鏡頭距離跨重生點持續存在）。
- 執行後其餘方位快照過期處理與 `走` 完全一致。

## 第 3 節：絕對歸位（`Bot._zoom_restore_if_touched`）

`net_zoom != 0` 才執行：

```
按 I × zoom_reset_saturate_presses（飽和進第一人稱，冪等）
→ settle → 按 O × zoom_reset_pullback_steps（K，校準值＝標準挖礦距離）
```

- 回拉段逐步驗證被吃、被吃重送——歸位冪等、誤判重做無害（與俯仰歸位 attempt-2 重試同語意；方向安全性與旋轉「寧漏判勿誤重送」相反，故驗證門檻分家）。
- 掛在三個出口：**成功回 MINING 的 init 序列前**、**`跳過` 轉 NEEDS_HUMAN 前**、**等待中又重置作廢 context 時**。
- 記帳錯誤／步進不對稱都不會漏進 MINING——這是選絕對基準而非反向記帳的理由。

## 第 4 節：資料落盤

- `record_click`／`log_command` 增 `zoom` 欄（當下 `net_zoom`）；快照檔名帶 `_z+N` 標記。
- 未來模板庫的尺度分佈靠這個標注；舊資料無 zoom 欄＝標準距離，語意不變。

## 第 5 節：config 與校準

新增 config（全在 `config.py`）：

| 名稱 | 意義 |
|---|---|
| `reentry_zoom_step_default` | `遠`/`近` 省略步數時的預設 |
| `reentry_zoom_max_steps` | 單指令步數上限（防手滑打 99） |
| `zoom_reset_saturate_presses` | 歸位飽和段按 I 次數（須大於最大可能步數） |
| `zoom_reset_pullback_steps` | 歸位回拉 K 步；**0＝未校準＝整組指令停用** |
| `zoom_eaten_mean_diff` / `zoom_eaten_changed_frac` | 送鍵被吃判定獨立門檻（初值抄 pitch） |

校準 K 的流程（寫進 `docs/manual-sampling.md`）：實機把鏡頭調到平常挖礦距離 → 狂按 I 進第一人稱 → 一步步按 O 數到回到熟悉距離＝K；可搭 R 視窗截圖比對。

## 第 6 節：測試（純邏輯 TDD）

- 解析：`遠`/`近`/`far`/`near`/帶步數/步數超過上限 clamp 到 `reentry_zoom_max_steps`（不拒收，寧可少拉不擋操作）/未校準停用/等細格時機不合法。
- `plan_zoom_restore(net_zoom, saturate, pullback)` 純函式回按鍵序列（`net_zoom=0` 回空）。
- `net_zoom` 記帳：連續遠近混用、`重骰` 不清零。
- ledger/click 的 zoom 欄位齊全。
- remote-reentry 既有測試全綠不改。

## 風險與對策

| 風險 | 對策 |
|---|---|
| I/O 送鍵被吃 | 逐步幀差驗證＋重送；獨立 `zoom_eaten_*` 門檻（粒子特效教訓） |
| 記帳脫鉤漏進 MINING | 歸位走絕對基準（夾限飽和→固定回拉），記帳只供落盤參考 |
| K 未校準就使用 | `zoom_reset_pullback_steps=0` 時整組指令停用，回提示不動作 |
| 使用者在等細格時下 zoom | 只在 `awaiting_cmd` 收，其他時機回提示 |
| 拉遠後按鈕小於細格精度 | 使用者自行 `近 n` 收回到看得清的距離再指位（人在迴圈，毋須自動判斷） |

## 明確不做（本版）

- 開場鏈自動拉遠（只有部分重生點需要）。
- 視覺偵測「目前 zoom 等級」（夾限飽和已給絕對基準）。
- 挖礦/採集態的 zoom 管理（那邊從沒動過 zoom，不引入新變因）。
- 滾輪路徑（I/O 鍵已足）。
