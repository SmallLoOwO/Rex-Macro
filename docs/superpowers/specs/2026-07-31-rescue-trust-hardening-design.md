# 救援信任度強化：讓「面板零點」在實機上真的成立，並且不敢一上線就自動放生礦

日期：2026-07-31
狀態：設計定案，待實作
關聯：`2026-07-31-panel-zero-rescue-design.md`（本文修正它的三個實機失效點）、
`docs/open-detection-issues.md` D11（列底色 → tier 量測）、H069

## Problem Statement

玩家的話：「前面有提到每次稀有回礦的時候需要重置背包，但是似乎沒有成功與驗證後就
繼續往前了。」

把當天的 log 攤開，面板歸零功能上線後跑過兩次，**兩次都失敗**，而且失敗之後 bot 照樣
往下跑：

```
17:37:04 WARNING 面板歸零失敗：標頭 NORMAL、列數 1（shamrock）
17:43:47 WARNING 面板歸零失敗：標頭 NORMAL、列數 8（faedrine、riches、siogyne…）
```

沒有任何一次成功 ⇒ `_panel_zeroed_at` 恆為 `None` ⇒ 交人工前救援的路 B 從上線到現在
一次都沒作用過。查下去露出四件事，一件比一件嚴重：

1. **bot 自己的動作污染了驗證。** 清空序列最後那一下「點畫面中央還焦點」是一次真的
   挖礦點擊。17:37:04 那次面板其實被清乾淨了（15 列 → 0），卻在 OCR 之前挖到一顆
   shamrock 回填，於是讀到 1 列判「失敗」。要求「面板 0 列」等於要求 bot 自己的
   還焦點點擊不能挖到石頭——實機上永遠達不到。
2. **面板重繪比 settle 慢。** 17:43:47 讀到的是清空前原封不動的前 8 列。暫停後補拍的
   實機截圖顯示那次清空其實成功了（現在面板是 0 列、篩選框裡的 `w` 已壓成一條線），
   所以那一讀讀到的是還沒重繪的畫面。單次 0.3s settle 不夠。
3. **救援路 B 回錯東西。** `_panel_rare_ores` 算了白名單卻回傳整份面板礦名，呼叫端
   只看「非空就算命中」——而面板上永遠有鎬子挖出來的低階礦。這條路只要一被啟用就會
   **每一次 giveup 都判「已進帳」**，每顆真稀有礦都被靜默放生（H069 同型）。它沒爆
   只是因為第 1、2 點讓零點永遠不成立、整條被跳過。
4. **礦名分類有模糊假陽性。** `essence of luck`（低階、常駐背包）被 `classify_found_ore`
   模糊配到 Lovessence（Transcendent、Aesteria）ratio 0.824 → 又是一條假命中來源。

第 3、4 點都是同一個方向：**多宣告一次「已進帳」**。這條路的代價不對稱——漏判是多按
一次手機，誤判是永久失去一顆稀有礦。而且兩個 bug 都躲過了既有測試（一個被打樁替換掉、
一個沒有 ground truth 可比）。

## Solution

四件事，合起來讓「面板零點」在實機上真的成立，並且讓第一次上線不敢直接放生礦。

**A. 不要用會挖到礦的方式脫離文字框。** 打完 `w` 之後改按 `Enter` 脫離
（玩家確認：這款遊戲的 Enter 不會開啟聊天輸入列），不再點畫面中央。面板因此維持真空，
零點驗證量的是「篩選框有沒有生效」而不是「bot 剛剛挖到什麼」。

**B. 讓驗證看得懂重繪延遲，也看得懂讀不準的礦名。** 讀不到零點時最多重讀（只重讀、
不重點也不重打字）；判準用**列底色**當第二條 tier 訊號——2026-07-31 量測 238 幀 1909 列，
面板列底色是**每個 tier 一個色相、零變異、零重疊**：

| tier | H | tier | H |
|---|---|---|---|
| Transcendent | 210 | Mythic | 304 |
| Exquisite | 128 | Surreal | 166 |
| Exotic | 46 | 低階（三帶） | 0 / 30 / 280 |

**C. 兩條訊號都只往保守方向用，而且兩側的保守方向相反。**

- 零點閘要的是「面板上**沒有** Exotic+」：色相**不在已知低階色帶**就當高階 → 零點不成立。
  未量到的新 tier 也擋得住。
- 救援側要的是「面板上**有** Exotic+」：色相必須落在已量到的高階色帶才算。未知色相
  寧可交人工。

兩邊猜錯的後果都只是「多交一次人工」，絕不會多宣告一次「已進帳」。同時面板路徑的礦名
判準收緊成 **只認 exact match**：實機 320 列真陽性全部是 exact，`rare_fuzzy` 在面板上
的唯一貢獻就是那個假陽性。

**D. 先觀察，再自動。** 路 B 判定命中時**照樣交人工**，只在 log 與通知裡標明「路 B 認為
已進帳」。命中次數持久化累計；滿 10 次由之後的 agent session 主動把歷次證據攤給玩家看，
問要不要切自動。

另外兩件同批決議：

**E. 容量 15 分鐘沒上升 → Discord 警報。** 面板真空之後「有礦進來」就等於「鎬子真的在
挖」，但那個判準只在進 MINING 時讀得到，而真的卡住時根本不會再進 MINING。容量 OCR 本來
就每輪在跑，拿它當計時器是免費的。不停機——誤報一次就白白損失整晚挖礦。

**F. 標註還原限 15 分鐘內。** Ctrl+Z 是為了「不小心按到 Enter、內容是錯的、要還原重送」
這種當下的誤操作，不是用來刪很久以前、可能已經進版控的素材。

## User Stories

1. 作為玩家，我希望 bot 清空背包面板之後真的驗得過，這樣救援路 B 不會從上線第一天就是死的。
2. 作為玩家，我希望 bot 不要為了「把焦點還給遊戲」而多挖一顆礦，這樣它自己的動作不會弄髒自己的驗證。
3. 作為玩家，我希望面板重繪慢一點的時候 bot 會多看一眼，而不是立刻判失敗。
4. 作為玩家，我希望 bot 不要為了「多看一眼」就多點一次或多打一次字，這樣點歪的座標不會被重複按。
5. 作為玩家，我希望 bot 判「面板上有沒有稀有礦」時不是只靠讀字，這樣礦名讀歪不會讓它瞎掉。
6. 作為玩家，我希望顏色訊號只在讓 bot 更保守時才有話語權，這樣一條沒實機驗過的新訊號不會拿我的礦當賭注。
7. 作為玩家，我希望遇到沒見過的礦物顏色時 bot 當它是稀有的而不是普通的，這樣新出的高階礦不會讓零點誤判成乾淨。
8. 作為玩家，我希望救援要宣告「已挖到」時顏色必須是我看過的稀有色，這樣沒把握的情況一律叫我。
9. 作為玩家，我希望面板礦名比對不要模糊猜，這樣 `Essence of Luck` 不會被當成 Transcendent 的 Lovessence。
10. 作為玩家，我希望聊天那條路的模糊比對不要跟著被改掉，這樣真正需要容忍 OCR 雜訊的地方不受波及。
11. 作為玩家，我希望救援路 B 只回它真正認定的稀有礦，這樣「面板非空」不會被當成「挖到了」。
12. 作為玩家，我希望新功能第一次上線時先跑觀察期，這樣它判錯的時候我還在場，而不是事後才發現少了一顆礦。
13. 作為玩家，我希望觀察期間 bot 照樣叫我，但告訴我「它本來會判已進帳」，這樣我可以當場對照它對不對。
14. 作為玩家，我希望觀察期的命中次數會被記下來，這樣我不必自己翻 log 數。
15. 作為玩家，我希望累積到足夠次數之後有人主動來問我要不要切自動，這樣這個模式不會像 `scan_confirm_mode` 一樣永遠停在觀察狀態。
16. 作為玩家，我希望切自動之前看得到歷次判定的證據，這樣我是根據事實決定而不是被通知催。
17. 作為玩家，我希望 bot 長時間沒有任何礦進帳時會叫我，這樣它空轉整晚我不會到早上才發現。
18. 作為玩家，我希望那個「卡住」判斷不要靠面板，這樣它在 bot 真的卡住（不會再進 MINING）時仍然會觸發。
19. 作為玩家，我希望卡住警報不要自動停機，這樣一次誤報不會讓我損失一整晚。
20. 作為玩家，我希望卡住警報的門檻遠大於一個正常採集週期，這樣正常運作時它不會吵我。
21. 作為玩家，我希望標註打錯時可以按 Ctrl+Z 還原重送，這樣手滑按到 Enter 不會留下一筆錯的素材。
22. 作為玩家，我希望還原只對剛剛寫下的素材有效，這樣很久以前、已經進版控的素材不會被我一個誤按刪掉。
23. 作為玩家，我希望還原失敗時看得到原因，這樣我知道是「超過時間」還是「本來就沒寫成功」。
24. 作為維護者，我希望零點驗證失敗時留下裁圖，這樣下一場才分得出是點沒中、字沒進、還是重繪沒跟上。
25. 作為維護者，我希望兩條訊號不一致時 log 會吼出來，這樣顏色與礦名誰在漂移看得見。
26. 作為維護者，我希望顏色門檻的來源與量測範圍寫在文件裡，這樣下次有人想調它時知道兩側夾是怎麼夾的。

## Implementation Decisions

### 面板零點（`main.Bot._clear_panel_filter`）

- 序列改成：`click(篩選框)` → `typewrite("w" × N)` → `settle` → OCR 驗 → **`key_press("enter")`**。
  不再有「點畫面中央」那一步。脫離動作放在 `finally`，例外時也一定執行，且自己包
  `try` 不蓋掉原始例外（維持現行行為）。
- Enter 用 `input_control.key_press`，與其他按鍵路徑同一條（**不可**引入 `keyboard`，
  AGENTS 規則 11）。
- 讀不到零點時最多重讀兩次（次數與時間預算同時設上界，時鐘停住時不會空轉）。
  **只重讀，不重點也不重打字**——H047/H063 的「多試幾次會翻面」只針對點擊與按鍵。
- 失敗時把該裁圖存成 `panel_zero_failed` 快照（維持現行行為）。

### 零點判準（`harvester`）

- 判「零點成立」＝ 標頭 == `panel_expected_header` **且**面板上沒有任何一列被判為 Exotic+。
- 「被判為 Exotic+」有兩條獨立訊號，任一成立就擋（OR，保守）：
  - **礦名**：`rare_panel_ores`，只認 exact match（見下）。
  - **列底色**：色相不落在已知低階色帶（0 / 30 / 166 / 280 / 304，各帶 ±tol）→ 當成高階。
    低階色帶清單與容差進 `Config`；容差沿用現行 6°（Exotic 46 與低階 30 相隔 16°，
    兩側各留 10°）。
- 新增純函式：判斷單一色相是否落在「已知低階色帶」內（反向判準），與現行
  `whitelist_hue_hits`（正向判準）並存。兩者都吃 `Config` 的色帶清單，不寫死。

### 面板礦名（`harvester.rare_panel_ores`）

- 只接受 `classify_found_ore` 回 `rare`（exact），**不接受 `rare_fuzzy`**。
- 依據：238 幀 1909 列量測，320 列真陽性全部是 exact（`fuzzy_ratio` 為 None），
  唯一一次 `rare_fuzzy` 命中是假陽性（`essence of luck` → Lovessence，0.824）。
- 聊天路徑（`_rescue_chat_ores`、`ChatLedger`）**不動**：那邊的輸入是 OCR 過的遊戲聊天行，
  真的需要容忍變體前綴與尾端雜訊。

### 救援路 B 觀察期（`main.Bot._giveup_rescue`）

- `Config` 新增觀察開關（預設**開**＝觀察中）與門檻 10。
- 觀察中命中：**不呼叫收尾、不回 True**，照舊往下走交人工；log 與交人工通知裡標明
  「路 B 認為已進帳（觀察中，第 N 次）」＋命中的礦名與來源，證據截圖照舊。
- 命中次數持久化，與 `harvest_seq` 同一種做法（log_dir 底下的小 json，重啟後續號）。
  記錄每次的 harvest_id、礦名、來源、時間，滿門檻後不自動切換。
- 切自動由人決定；累計滿門檻這件事寫進 agent 的長期記憶與 `docs/`，由之後的 session
  主動把歷次紀錄攤出來問玩家。**不做新的 Discord 流程。**

### 卡住偵測（`states` + `main._banner_ocr_loop`）

- 純函式：吃「目前容量、上次觀測到的容量、上次上升的時刻、現在時刻、門檻秒數」，
  回「要不要警報」與新的狀態。形狀比照同檔已有的 `update_capacity_streak`。
- 執行緒裡只留一行呼叫；容量本來就每輪在讀，**不新增任何 OCR**。
- 只在 `State.MINING` 期間計時；離開 MINING（採集／重置／交人工／暫停）一律重置計時，
  否則交人工等半小時會誤報。
- 觸發：發 Discord 警報，**不停機、不改狀態**。同一次停滯只發一則（去抖），容量一上升
  就清旗標。門檻預設 900 秒（15 分鐘，遠大於一個採集週期 ~6 分鐘）。

### 標註還原視窗（`web_server` 的 undo route）

- 刪檔前檢查目標 json 的 mtime：超過視窗（預設 15 分鐘）一律回 409 並附原因，不刪任何檔。
- 純 stdlib（`os.stat`），**不查 git**——玩家描述的情境是「當下按錯要重送」，時間視窗
  剛好編碼那個情境，而且不必把 git 依賴帶進 web 層。
- 前端把 409 的訊息原樣顯示在狀態列（現行 undo 失敗路徑已經會顯示 `err.error`）。

## Testing Decisions

好的測試只驗**外部可觀察的行為**：狀態變數的最終值、有沒有送出某個輸入、HTTP 狀態碼、
純函式的回傳值。不驗「呼叫了哪個內部函式幾次」（現行 `_panel_rare_ores` 的 bug 正是
因為測試把整支函式打樁替換掉，只驗到呼叫端）。

**四個接縫全部沿用既有的，不新增。**

1. **`harvester` 純函式** → `tests/test_harvester.py`
   - 前例：`panel_is_zeroed` / `whitelist_hue_hits` / `parse_panel_rows` 現有測試。
   - 覆蓋：exact-only（`rare` 收、`rare_fuzzy` 不收，用 `essence of luck` 當實機反例）；
     反向色帶判準（五個已量到的低階色帶都不擋、三個高階色帶都擋、未知色相當高階）；
     零點判準的組合（礦名乾淨但底色髒 → 不成立，反之亦然）。

2. **`states` 純函式** → `tests/test_states.py`
   - 前例：`update_capacity_streak` 的既有測試就在同一區。
   - 覆蓋：容量上升 → 計時歸零；持平未達門檻 → 不報；持平超過門檻 → 報一次；
     再持平 → 不重複報；OCR 讀失敗（None）→ 不當成持平也不當成上升。

3. **`tests/fake_bot.py` 的 `make_fake_bot(bind=[...])`** → `tests/test_giveup_rescue.py`
   - 前例：該檔既有的 `_clear_bot` / `_rescue_bot` harness（`ic`、`pydirectinput`、
     `capture`、`ocr`、`time` 全部 monkeypatch）。
   - 覆蓋：清空序列**不再**點畫面中央、結尾送出 Enter；驗證發生在脫離動作之前；
     重讀只重讀不重打字；例外時 Enter 照樣送出；observe 模式命中時 `_giveup_rescue`
     回 False 且沒有呼叫收尾、計數 +1 且通知含「觀察中」；關掉 observe 時回 True。
   - `_panel_rare_ores` 的測試**不准**再把整支打樁掉——要餵假 `read_text_boxes` 與
     合成裁圖走完真實路徑（現行已補的兩個測試就是這個形狀，繼續沿用）。

4. **FastAPI `TestClient`** → `tests/test_web_annotate_png_pair.py`
   - 前例：該檔的 `parts` fixture（`create_app` + tmp fixtures dir）。
   - 覆蓋：剛寫完立刻 undo → 200 且兩檔都刪掉；把 mtime 調老 → 409 且**檔案還在**；
     訊息裡看得出是超時而不是找不到。

視覺相關的門檻改動一律要有實機素材與兩側夾（AGENTS DEVELOPMENT WORKFLOW）。本規格的
色帶清單來自 `docs/open-detection-issues.md` D11 的 238 幀量測，新增測試沿用合成 HSV
裁圖（現行 `test_panel_row_hues_reads_the_row_background` 的做法），不需要新素材。

## Out of Scope

- **標註驅動的微調迴圈**（`tests/fixtures/` 底下 52 個未進版控的玩家標註）。玩家明確
  說先不跑。它會動到偵測門檻與 fixture，跟本規格搶不同檔案但搶同一段注意力。
- **把路 B 切成自動**。本規格只做到「累積到 10 次並準備好證據」，切換是之後另一次決定。
- **聊天路徑的模糊比對門檻**。只有面板路徑收緊。
- **色相 → tier 的完整校色表**。現在只需要「哪些色帶是低階」與「哪些是已知高階」兩份
  清單，不需要為每一階命名或為未量到的階補值。
- **面板數量欄**。仍然被右側 craft 面板疊住，本規格一律只讀名字與底色。
- **自動化「卡住」的自癒**（重跑 `init_mining_sequence` 之類）。只警報。
- **改變面板裁圖範圍**。D11 的量測與本規格的判準都建立在現行 `backpack_review_region`
  涵蓋的前 8 列上。

## Further Notes

- **D11 的量測範圍是面板前 8 列**（裁圖高度就那樣）。因為面板照 tier 由高到低排，白名單
