# 兩套具名標準俯角（挖礦／回礦）設計

日期：2026-07-17
狀態：設計定案，待實作計畫
前置：`2026-07-11-pitch-sweep-design.md`（mid 層與 pitch_reset 絕對定位）、
`2026-07-12-remote-reentry-design.md`（remote 回礦本體）、
`2026-07-14-manual-reentry-and-freeze-gate-design.md`（H044/H046 開場閘與俯仰探針）

## 目標與定位

現況問題：**bot 啟動／開始挖礦時完全沒有俯仰歸位**，沿用玩家啟動前留下的任意角度；
回礦成功恢復挖礦後，角度也是回礦流程留下什麼就是什麼。原本打算把「特定俯角」問題
留到點選傳送框（自動化）時再解，但它其實同時影響四件事（2026-07-17 問答確認）：

1. **掃描一致性**：tracker 偵測、門檻、fixture 在不同俯角下表現不同；固定角度讓量測可比。
2. **回礦後接軌**：下礦成功恢復挖礦要有標準角度可回。
3. **啟動角度不可靠**：人啟動前可能低頭/抬頭擺在奇怪角度，第一輪掃描品質不受控。
4. **為自動化鋪路**：未來點傳送框自動化需要全程可重現的姿態基準。

設計問題「初始化與點傳送框要不要同一個固定角」的答案＝**方案 A：兩套具名標準角**
（挖礦標準角＋回礦標準角），機制共用 `pitch_reset` 絕對定位。

## 已確認決策（2026-07-17 問答）

| 問題 | 決策 |
|---|---|
| 「初始化」指哪個時點 | **bot 啟動／開始挖礦時**（回礦開場已有歸位，另計） |
| 動機 | 上列四項全選 |
| 方案 | **A：兩套具名標準角**（否決 B 全程單一角＝礦內掃描與地表傳送框可見性綁死；否決 C 維持原計畫＝四個動機都不解決） |
| 新增 config 欄位 | **不新增**，重用 `sweep_pitch_center_back_px` 與 `reentry_pitch_back_px` |

## 關鍵約束（決定架構的兩個事實）

1. **俯仰沒有絕對讀數；夾限飽和→回拉＝唯一絕對定位**（`ic.pitch_reset`，見
   `input_control.py`）。因此「兩個階段用不同角度」只是兩個回拉值，每次切換經過
   夾限重新定位、誤差不累積，成本只有每次 2~3 秒拖曳。
2. **回礦流程內部，拍照角度＝點擊角度是硬約束**。使用者指的粗格（`3 C2`）與細格
   （`C3`）座標全部建立在拍照當下姿態；開場之後、點擊之前改俯角＝畫面座標全變、
   粗格裁圖對不上 sweep 圖、漂移守門（`reentry_remote_drift_diff`）連環跳。未來
   模板自動化同理：模板在哪個角度採，掃描與點擊就得在那個角度。

推論：**挖礦標準角 vs 回礦標準角可以自由不同**（之間隔著礦內↔地表場景切換，無任何
座標映射跨越邊界）；**回礦內部不可再分角度**。

## 第 1 節：角度定義（重用現有欄位）

| 具名角 | 欄位（`Config`） | 現值 | 校準用途 |
|---|---|---|---|
| 挖礦標準角 | `sweep_pitch_center_back_px`＋`sweep_pitch_clamp_px` | 0（未校準＝停用） | 礦內掃描視角。這就是失敗路徑俯仰掃描的「mid 層」與遙控器 `pose_pitch_layer="mid"` 指的同一個角度——校準一次補齊三件事的基準 |
| 回礦標準角 | `reentry_pitch_back_px`＋`reentry_pitch_clamp_px` | 400（R 視窗時代值，未針對用途校準） | 地表上傳送框好不好看見／好不好指；開場拍照、粗格放大、細格點擊全程鎖定 |

## 第 2 節：新套用點（只有兩個）

1. **bot 啟動、進第一輪掃描前**：`sweep_pitch_center_back_px > 0` 才做
   `pitch_reset(sweep_pitch_clamp_px, sweep_pitch_center_back_px)`；＝0 維持現狀
   （沿用人留的角度）並 log 警告「挖礦標準角未校準」。比照 reentry「未校準＝停用」
   慣例：缺校準不靜默改變行為。
2. **回礦成功恢復挖礦時**（remote 的 `_rr_success` 與 auto 版成功路徑）：同樣歸位到
   挖礦標準角（同一停用條件）。

既有行為不變的部分：回礦開場歸位到回礦標準角（`_rr_open_episode`／auto `PITCH_RESET`
相位）照舊；`仰角 上/下 [px]`＋📷 人工微調照舊（`_pitch_offset_px` 記帳照舊）；
giveup 遙控器 mid 層記帳照舊。

錯誤處理：新套用點的歸位被吃（幀差量測失敗）**警告不擋流程**——比照開場閘
「俯仰被吃不擋拍照」慣例（H046）。啟動歸位失敗頂多回到現狀（角度不受控），
不值得為它擋掛機。

## 第 3 節：校準流程（不可目測猜值）

- **回礦標準角**：實機回礦 episode 中用現有 `仰角 上/下 [px]`＋📷 迭代到傳送框好指；
  `_pitch_offset_px` 記帳值（log 可讀）就是絕對回拉量，寫回 `reentry_pitch_back_px`。
  零新程式。
- **挖礦標準角**：`仰角` 指令只活在 REENTRY 待命，礦內沒有等效工具。新增輕量校準
  CLI（比照 `calibrate_surface` 慣例）：`uv run python -m miningbot.calibrate_pitch`
  → 聚焦 Roblox → `pitch_reset` 拖到夾限 → 鍵盤逐步 nudge、即時印累計偏移 →
  人看畫面滿意後把印出的值寫回 `sweep_pitch_center_back_px`。

## 第 4 節：測試計畫

- 新套用點的執行條件寫成純決策（back_px>0 才歸位、被吃只警告），比照專案
  「純函式＋I/O 在 main」慣例可單測。
- 回礦成功收尾順序（movement mode 復原 → 歸位 → ledger → 回 MINING）加順序測試。
- config 欄位語意（0＝停用）進既有欄位測試。
- **不動任何現有 pitch 回歸**（pitch_eaten、probe_frozen、sweep_pitch 純函式測試全保留）。

## 範圍外（明文排除）

- `sweep_pitch_enabled` 開啟——校準完成只是解鎖前置，開不開另行實機驗證。
- 點傳送框自動化本體——本設計只保證未來做時姿態可重現。
