# 失敗路徑俯仰掃描「真正啟用」設計

日期：2026-07-28
狀態：設計定案，待實作
關聯：`2026-07-11-pitch-sweep-design.md`（原始設計，程式已實作）、
`2026-07-17-standard-pitch-presets-design.md`（挖礦標準角校準）、
`2026-07-18-discord-pitch-calibration-design.md`（Discord 校準卡）

## Problem Statement

玩家在網頁玩家設定頁勾了「掃描俯仰」，以為八方位全空的時候 bot 會多抬頭、低頭各掃
一輪再放棄。實際上這個功能**從 2026-07-11 實作至今一次都沒有跑過**：

`plan_pitch_layers` 的啟用條件是 `enabled ∧ step_px != 0 ∧ center_back_px > 0`，而
`sweep_pitch_step_px` 的預設值是 `0`（＝從未校準）。玩家的
`config_overrides.json` 只寫得進 `sweep_pitch_enabled`（白名單只收四個欄位，步進量
屬於 AI agent 專屬參數），所以勾了之後 `plan_pitch_layers` 仍然回空序列，
`decide_sweep_failure` 永遠不會回 `NEXT_LAYER`，八方位全空照舊直接交人工。

網頁那個勾選框旁邊本來就印著「`sweep_pitch_step_px=0` 時勾了也不會動」的警告，但
玩家的合理期待是「勾了就該動」，而不是「勾了之後還要另一個人去改程式碼」。

同時，即使填上校準值，還有一個結構性問題：層轉換不會重新按 D2。從按下 D2 到上層
開始掃已經過了約 32 秒，`docs/game-mechanics.md` 明寫 tracker 會因「掃描到期」自行
消失，卻沒有人量過它活多久。若 tracker 在上層開掃前就淡出，這個功能是靠運氣在跑。

## Solution

兩件事，讓既有的俯仰層路徑真的動起來：

1. **填上 `sweep_pitch_step_px` 的校準值**，讓 `plan_pitch_layers` 回出 up/down 兩層。
2. **層轉換完成後重新按一次 D2**，讓上/下層看到的是新鮮的追蹤框，而不是可能已經
   到期的舊掃描結果——照使用者的說法：「如同掃描設計，如果沒有了即立刻補充，
   這樣 tracker 無論如何都會活著」。

玩家端的體驗：勾了「掃描俯仰」之後，本來會直接跳出「找不到追蹤框，請手動處理」的
場次，會先多花約 70 秒把視角抬高 45° 掃一輪、壓低 45° 再掃一輪，任一層撈到框就
就地開火，全空才交人工。不勾＝逐字回到今天的行為。

## User Stories

1. 作為玩家，我想在網頁勾了「掃描俯仰」之後它就真的生效，這樣我不用去問「為什麼
   勾了沒反應」。
2. 作為玩家，我想在標準視角看不到追蹤框時 bot 自己先抬頭低頭找過，這樣我不用為了
   一顆掛在天花板上的礦被叫回來手動處理。
3. 作為玩家，我想在 bot 已經很確定看到框的時候立刻開挖，不要為了「掃好掃滿」把
   三層走完，這樣稀有礦不會在等待中被別人挖走。
4. 作為玩家，我想在採集結束（不論成功或放棄）後視角自動回到我平常挖礦的置中角度，
   這樣我接手時畫面不是歪的。
5. 作為玩家，我想知道 bot 現在在掃第幾層，這樣我從 Discord 通知就能判斷它是卡住
   還是正在多做一輪。
6. 作為玩家，我想在俯仰拖曳被遊戲吃掉的時候 bot 跳過那一層繼續，而不是在角度不明
   的情況下硬掃，這樣不會出現「對著地板開火」。
7. 作為玩家，我想在礦坑重置的時候 bot 立刻停止掃層去處理重置，而不是把 70 秒花完
   才發現礦坑早就重置了。
8. 作為玩家，我想在三層都空的時候拿到三層份的診斷截圖，這樣我能自己看出來礦到底
   在不在。
9. 作為玩家，我想在上/下層撈到框時 bot 就地開火而不是先轉回標準角，這樣不會在
   歸位途中把好不容易找到的框弄丟。
10. 作為玩家，我想維持「不勾就完全不變」的保證，這樣我覺得它在浪費時間時可以一鍵
    關掉。
11. 作為 bot 操作者，我想在每一層開掃前都有一次新鮮的 D2 掃描，這樣「上層沒撈到」
    的結論是「那層真的沒有」而不是「框早就到期了」。
12. 作為 bot 操作者，我想在重掃時**不要**重新拍排除基準幀，這樣不會把畫面上的活框
    寫進排除清單自我致盲（H026）。
13. 作為 bot 操作者，我想讓每層的掃描逾時預算從重掃完成之後才起算，這樣預算量到的
    是「掃描花了多久」而不是「等冷卻花了多久」。
14. 作為 bot 操作者，我想在 log 裡看到每次層轉換距離上一次 D2 有幾秒，這樣「這次
      重掃到底有沒有生效」是可查的事實而不是推測。
15. 作為 bot 操作者，我想在相機撞牆變成角色特寫的場次照樣掃俯仰層，因為追蹤框會
    顯示在角色前面，特寫不代表框看不到。
16. 作為 AI agent 維護者，我想讓「層轉換一定會重掃」這件事被測試鎖住，這樣未來重構
    `_pitch_layer_transition` 不會靜默地把它拿掉。
17. 作為 AI agent 維護者，我想讓校準值旁邊留下推導過程（370px 對應多少度、FOV 多少、
    三層覆蓋有沒有縫），這樣下次換世界要重校時不用重新推一次。
18. 作為 AI agent 維護者，我想讓這份設計記下「語料查過、沒有正面證據但也否證不了」
    的結論，這樣未來有人問「為什麼要做這個」時不會又查一次同樣的快照。
19. 作為 AI agent 維護者，我想讓實機驗收清單明確到「看哪一行 log、看哪一張快照」，
    這樣第一場實機跑完就能判定成敗。
20. 作為 AI agent 維護者，我想讓校準值被判定錯誤時只需要改一個數字，不用動任何
    程式邏輯。

## Implementation Decisions

### D1：`sweep_pitch_step_px` 定為 185

推導（使用者 2026-07-28 決定「先取 370 的一半」，本節補上依據）：

- `sweep_pitch_center_back_px = 370` ＝ 從俯仰夾限飽和位置回拉到挖礦標準角的拖曳量。
- 實機快照顯示挖礦標準角約略水平；夾限假定為垂直方向到底，故 370px ≈ 90°，
  約 4.1 px/度。
- 185px ≈ 45°。Roblox 預設垂直 FOV 70°（D5 boost 只會撐更大），三層落在
  −45° / 0° / +45°，覆蓋 −80~−10 / −35~+35 / +10~+80 → **層間有 25° 重疊、沒有縫**。

正負號沿用既有約定：正＝向下拖，`plan_pitch_layers` 產生 `up = -step`、
`down = +step`。若實機發現遊戲方向相反，只改這一個數字的正負，不動任何函式。

這個值**未經實機驗證**，第一場實機的驗收項目之一就是確認上/下層視野真的差了約
45°（見驗收清單）。

### D2：層轉換後重掃 D2

`_pitch_layer_transition` 在拖曳驗證成功、寫入 `harvest.pitch_layer` 之後，追加與
`_reharvest_sweep`／`_recover_historical_target` 相同的重掃序列：

```
prepare_scan() → _await_scan_ready("pitch-layer-<name>") → _run_scan() → _confirm_scan(...)
```

- **不重拍 `_pre_scan_ref`**。H026 的教訓：重掃時畫面上往往已有活框，重拍會把它寫進
  排除基準，之後每個方位都 `rej(preexist)` 自我致盲。沿用進場時拍的那張——它實際
  排除的是螢幕空間的靜態 UI（熱鍵列、礦物面板），不隨視角或俯仰改變；世界內容錯位
  漏放的假陽性交給 `colored_frac` 與形狀確認擋。這與 `_reharvest_sweep` 的既有論證
  逐字相同。
- **`_harvest_start` 的重置移到重掃之後**。否則每層的 `sweep_timeout_s` 預算會被
  掃描本身（`execute_scan` 內含 1.8s 等待）與可能的冷卻等待吃掉。
- `prepare_scan()` 會按兩次 shift（Roblox shift lock 開關，淨效果是把游標移到畫面
  中央），**不改變鏡頭俯仰**，因此放在俯仰 nudge 之後是安全的。

### D3：重掃可能落在冷卻裡，接受並記錄

D2 冷卻 30s 是共享的。實測時序：mid 層八方位 ~19s ＋ 一次
`pitch_reset(1500, 370)` 走 H048 分段拖曳（13 個 hold × ~1s）≈ 15s ＝ **約 32s**，
剛好蓋過冷卻，所以 up 層的重掃通常直接生效、幾乎零成本。

但這不是保證：早停或跳層會讓間隔縮短。`_await_scan_ready` 在
`radar_scan_repeat_enabled` 關閉（現行預設）時是直接放行，不會等我們自己那次掃描的
冷卻。決策是**不新增等待**（多等只為了保證新鮮度，代價是每層再多 30s），改為
在層轉換的 log 記下「距上次 D2 幾秒」，讓「這次重掃有沒有生效」變成事後可查的事實。
若實機顯示這個間隔經常 < 30s，再回頭加等待。

### D4：不設總預算上限，跑滿三層

使用者 2026-07-28 決定。既有的每層 `sweep_timeout_s = 30s` 已是軟上限，
`tracker_shape_early_exit = 0.60` 的早停會在任一層雙幀穩定且 edge ≥ 0.60 時當場接受、
不掃完剩餘方位——這正是使用者要的「中途有信心度非常高的框就直接挖掘」，已實作，
不需改動。收尾歸位（`_pitch_restore_if_touched`）同樣已實作，成功與放棄兩條路徑都會
在動過俯仰時回到置中標準角。

### D5：不擋相機撞牆的場次

使用者 2026-07-28 判定：追蹤框會顯示在角色前面，相機撞牆變成角色特寫**不代表框
看不到**。因此不新增「畫面被角色占滿就跳過俯仰層」的守門，也不新增對應的偵測器。

推論（值得記下來）：如果框確實會蓋在角色前面，那 harvest 115 那六張特寫就等於證明
那六個方位真的沒有框——這把該場次的根因從「框在視野外」推向「礦已被挖走或掃描
到期」，而 D2 正是打這一型的。

### D6：不動任何既有行為

層順序（up → down）、拖曳被吃的兩輪重試與跳層、礦坑重置檢查、快照層標記
（`sweep_snapshot_label`）、remote-aim 的 `pose_pitch_layer` 帶回與復原、
`decide_sweep_failure` 的其餘分支，全部維持現狀。本次改動只有一個常數與一段重掃。

## Testing Decisions

好的測試只驗外部可觀察行為：層轉換之後「有沒有觸發一次新掃描」、「排除基準有沒有
被動到」、「計時器是不是在掃描之後才歸零」——不驗呼叫了哪些私有方法、不驗參數的
逐字內容。

**接縫：一個，用既有 harness。** `tests/fake_bot.py` 的
`make_fake_bot(bind=["_pitch_layer_transition"])`：用 `Bot.__new__` 繞過 `__init__`，
只掛上受測方法真正會碰到的屬性，掃描與拖曳相關的協作方法用會記錄呼叫順序的 stub
取代。prior art 就是這個 harness 本身（P1~P5 的 web UI 整合測試、
`tests/test_main_pitch_home.py` 的 `_pitch_home_mining` 測試）。

要鎖住的行為：

1. 層轉換成功 → 記錄到一次掃描觸發，且發生在俯仰拖曳之後。
2. `_pre_scan_ref` 在層轉換前後是同一個物件（不重拍）。
3. `_harvest_start` 的重置發生在掃描觸發之後。
4. 拖曳兩輪都被吃 → 跳過該層，**不觸發掃描**（不對著沒切成功的層白按 D2）。
5. `_mine_resetting` 為真 → 直接回 False，不掃描也不拖曳。

`plan_pitch_layers` 的純函式測試（`tests/test_harvester.py`）已存在且涵蓋開/關與
未校準三種情形，不需新增；`sweep_pitch_step_px` 的值本身**不寫測試**——鎖住一個
待實機調整的校準常數只會做出一個改變偵測器。

## Out of Scope

- **相機撞牆（角色特寫）那一型**的處理。語料裡它比俯仰更常見（harvest 115 有 6/8
  方位是特寫），但使用者決定另開一份調查，本 spec 不碰。
- **每輪正常採集都掃三層**。本 spec 維持「失敗路徑限定」，正常採集零額外成本。
- **開火前用俯仰把偏上/偏下的框移到畫面中央**再打。那是另一個功能。
- **總預算上限 / 新的 config 鍵**。本次不新增任何 config 欄位。
- **`scan_confirm_mode` 的啟用**。維持 `off`，`_confirm_scan` 在本路徑等同 no-op，
  加它只是為了與其他掃描點的寫法一致。
- **把 `sweep_pitch_step_px` 放進網頁白名單**。步進量是校準參數，維持 AI agent 專屬。
- **`_run_scan` 在冷卻中仍會更新共享時鐘 `_radar_last["scan"]`** 這個既有小瑕疵。

## Further Notes

### 語料調查結論（2026-07-28）

實作前查過 2026-07-22 ~ 07-28 的 11 場八方位全空 giveup（harvest 108~118）：

- 逐張看過 115 / 116 / 117 的完整八方位。115 有 **6/8 方位是相機撞牆的角色特寫**
  （bot 自挖窄坑道，鏡頭拉不開，只有坑道軸向的 dir0/dir4 看得到世界）；116 / 117 是
  開闊礦洞，天花板到地板都拍進去了，畫面裡沒有任何框。
- 全 log 只有 23 個候選因超出 10% 邊界被拒，其中垂直向 8 個——**全部
  `colored=0.00` 且座標落在 x=19~38 或 x=1895~1899**，是左側礦物面板與右側圖示欄
  這些螢幕空間 UI，不是追蹤框。**沒有任何一個真框因為靠近上下緣被拒。**

**結論：語料沒有正面證據支持「框在垂直視野外」這個假說，但也無法否證它**——完全在
視野外的框本來就不留下任何痕跡。真正被語料指名的是相機撞牆那一型（見 Out of Scope）。
使用者 2026-07-28 決定兩者都做、俯仰優先，理由是俯仰層的程式碼已經寫完，只差校準。

原始 spec（2026-07-11）估計「多花 30-40s」是在 H048 改寫 `_drag_vertical` 之前寫的；
分段拖曳（150px/hold ＋ 0.8s 沉澱）之後真實成本約 **90-100 秒**，任一層拖曳被吃重試
再 +15s。這個數字要寫進使用者可見的說明，不要沿用舊估計。

### 實機驗收清單

1. `miningbot.log` 出現 `俯仰層切換 -> up（重新 8 方位掃描）`。
2. `harvest.log` 的層轉換行顯示距上次 D2 的秒數 ≥ 30（＝重掃真的生效）。
3. `snapshots/review/` 出現 `*_sweep_empty_up_dir*` 與 `*_sweep_empty_down_dir*`；
   **肉眼比對 mid 與 up 的同一方位**，視野應抬高約半個畫面。差太多或幾乎沒動 →
   改 `sweep_pitch_step_px` 的值或正負號，不改邏輯。
4. 收尾後視角回到置中標準角（成功、放棄兩條路徑各驗一次）。
5. 上/下層撈到框的場次：確認就地開火、沒有先歸位。

### 風險

| 風險 | 對策 |
|---|---|
| 185px 對應的角度與推導不符（夾限不是垂直向下） | 第一場實機看快照比對，只改常數 |
| 層轉換間隔 < 30s 使重掃無效 | log 記秒數；實機顯示常態不足再加等待 |
| 上/下層 45° 抬頭讓相機更容易撞牆 | 不特別處理；拖曳驗證失敗會跳層 |
| 多花 90-100s 期間礦坑裝滿 | 既有容量與重置監看照跑，重置中直接放棄掃層 |
