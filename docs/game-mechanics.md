# REX 遊戲機制筆記（給自動化用）

實機觀察到、會影響偵測設計的重點。**寫給「未來的我們」記住**。

## 通則（很重要）

- **背景永遠會變**：畫面背景隨玩家所在區域改變，整片可能被染成紅/藍等。
  → 任何 UI 偵測**只能比形狀/邊緣（color-invariant）、並裁緊**；顏色與背景完全不可靠。
- **工具使用後，右下角會出現「冷卻圖案」**，和 boost 瓶子在**同一條效果/冷卻列**，而且 **buff/冷卻會疊加 → 位置會位移，但都在同一區域內**。
  → 偵測要在**整條效果列裡搜尋**該圖示（不是固定一點）；用「圖示在不在」判斷工具好了沒，不必盲目計時。

## 各工具

### D5 — Boost（加成）✅ 已實作並驗證
- 用法：D5 + 左鍵點畫面 → 生效，右下角出現**青色瓶子 + 倒數數字**。
- 數字會變、位置會因疊加而移。
- 邏輯：**瓶子消失 = 效果結束 → 重上**（D5+點擊 → 回 D1+按住 W+左鍵）。
- 偵測：`boost_active.png` 在 `boost_indicator_region` 內做邊緣+多尺度比對；找不到且過冷卻 → 重上。
  實測此模板對「數字變化(54/50…)、堆疊位移」都偵測得到，偵測穩定。
- **重上的關鍵（實測 2026-06-26）**：挖礦時是**按住左鍵**的，重上要先**確實放開左鍵→沉澱一下→再點擊**，
  否則殘留的「按住」會和放置點擊衝突、被遊戲吃掉，boost 放不出來（log 會狂洗「boost 消失→重上」）。
  已在 `miner.use_boost`（`ic.settle()` + `mouse_click(hold=0.08)`）處理。

### D4 — Activity（控制活動）
- **左鍵 = 加強目前事件**：頂部文字**不變**，但左上聊天框會顯示（例：
  "X has increased the event time by 50%."、"X has boosted the current event ore by 10%!"）。
  可能增加活動長度或活動礦出現機率。
- **右鍵 = 刷新事件**：頂部文字**會被替換**，聊天框也顯示（例："X has replaced the ongoing event."）。
  少數情況會刷出同一個活動。
- **冷卻圖示（實測確認 2026-06-26）**：使用後右下角效果列出現一顆 **「Used」按鈕**（掃描瓶圖示+白字 Used，
  和 boost 瓶子同一列、會堆疊位移）。**冷卻好時這顆 Used 按鈕會整個消失**（同 boost 瓶子邏輯）。
  → 偵測 `d4_cooldown.png`（那顆 Used 按鈕）在 `boost_indicator_region` 內：**找得到 = 冷卻中、別按；找不到 = ready、就按**。
- **冷卻很長**：實測 114 秒不動它仍顯示 Used（正常冷卻 >2 分）。但 D4 會 lucky「**再來一次**」直接退冷卻、可馬上再滾，
  所以靠「冷卻圖示消失」偵測才抓得到那個瞬間；舊的固定 30s 定時會錯過、且大多時候按了是 no-op。
- 已實作：`miner.cooldown_ready` + `main._activity_ready`（config `activity_cooldown_*`）。缺模板時退回定時後備。

### D2 — Scan（掃描）
- 用法：**先按 2 裝備，再左鍵點畫面中央觸發**；附近有稀有礦時出現**亮綠外框（tracker）**；左下角顯示 **"Local" 已使用**。
- 採集流程（偵測到 chill 後）已會按 D2。是否要**定時主動掃描**待定。
- 使用後右下角同樣有冷卻圖案。
- **掃描到期** = tracker 框緩慢自動消失（不是立刻）→ 需重新掃描。
- **掃描期間會自動採集 Surreal 礦**（使用者確認 2026-06-30）→ 可能在聊天框新增「has found」行。
  對 D3 採集成功判定的影響與安全性分析見下方〈聊天框（has found 訊息）與採集確認〉。

### D3 — 採集（稀有礦）✅ 端到端已驗證 (2026-06-27)
- 用法：**先按 3 等 ~0.6s 裝備，再 hold 左鍵（按住 0.4s）點選 tracker 框的中心螢幕座標**。
  - 瞬間點擊（click）**無效**，需 hold 才能觸發（實測確認）。
  - 按 3 後不等就點也無效（裝備動畫未完成，點擊被吃掉）。
- **成功判定**：tracker 框**立即消失**（幾乎瞬間）= D3 打中；聊天框出現「has found / found a」確認。
- **失敗/到期**：tracker 框過幾秒才消失 = D2 掃描到期，不是 D3 打中 → 重新掃描。
- D3 以**滑鼠點選位置**決定攻擊目標（非 crosshair 方向）。不需旋轉 camera，直接點 tracker 的螢幕座標即可。

### Z — Cybernetium Radar（cave，特殊情況才用）
官方能力說明：
- **Z**：掃描 250 格半徑內特殊洞穴的方塊。冷卻 30 秒（掃完最後一個洞後起算）。
- **左鍵**：自動開採 100 格內 Uncommon–Mythic 礦；追蹤 250 格內 Surreal+ 礦。冷卻 30 秒。
- **右鍵**：全域追蹤礦場內所有 Exotic+ 礦。冷卻 25 秒；追蹤存活 30 秒。
- → 特殊用途，預設**先擱置**。

## 聊天框（has found 訊息）與採集確認

實機觀察 + 使用者確認（2026-06-30）。直接影響 D3 採集「`confirmed` 成功判定」的設計，**改前必讀**。

- **訊息只從最下方新增、不平滑捲動**：新的「`<小名> has found X`」直接出現在聊天框**最下面一行**，
  舊訊息往上推、逐漸淡出。**沒有平滑捲動動畫** → OCR 每一幀讀到的都是**完整行**，不會出現「半截行」。
  → 採集確認**不需要**對聊天做「雙幀穩定」防半截行；現有**單幀讀取**即足夠（2026-06-30 評估後決定不加）。
- **`chat_before`/`chat_after` 的時機**：兩次都在**八方掃描之後**才讀，只夾住 D3 開火的 ~1.35s（`main.py` 階段二，
  約 `:1043`/`:1058`）。**不跨越 sweep**。掃描那 ~19s 期間的任何聊天變動**全部 baked 進 `chat_before`**（stale），不進差分。
- **D2 掃描期間會自動採集 Surreal 礦**（使用者確認）→ 可能新增聊天行。但對 `confirmed` 是安全的，三層理由：
  1. **時機**：掃描期的新增在 `chat_before` 之前發生 → stale，不進 1.35s 差分。
  2. **過濾**：Surreal 在 `game_data.common_ores` 排除清單 → `count_rare_found` 不增、
     `has_new_rare_found_last_line` 底部新行是 Surreal → 非稀有 → 兩條訊號都不誤判成功。
  3. **無半截行**（見上）→ 不會因渲染中途把 Surreal 名讀成「不在清單的雜訊 token」而 `_is_rare_ore` 誤判為稀有。
- **實證**（trace `20260629_0221`，同段 `022108`→`022120` 相隔 12s 的兩張完整幀）：
  採集全程（含 D2 掃描期）聊天框**完全沒變**——11 行內容/順序/淡出程度一致。代表此例 D2 範圍內無 Surreal
  或自動採集未產生聊天行；無論何者，「捲動造成誤判」在此例並未發生。
- **唯一未來破口**：能讓 `confirmed` 假陽性的，只有「**挖礦已停、卻仍有非排除礦的 has found 落進那 1.35s 視窗**」。
  目前無此來源。若 **Z 雷達自動採集**（左鍵自動採 Uncommon–Mythic）上線並產生 has found，就要把 `confirmed`
  改成「**只認 chill 觸發的目標礦 + 目標框在點擊點消失**」，而非現在的「任何非排除礦」。屆時回頭改此處。
