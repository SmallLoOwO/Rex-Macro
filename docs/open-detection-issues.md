**這份是「已量測、未修復」的問題清單**，不是設計規格。每條都附實機幀量測與可重跑指令；
修好一條就把它整段搬進 `incidents.md`（給 H 編號）並從這裡刪掉。

現行行為仍以程式、測試與 `miningbot/config.py` 為準。已修復的部分見

## D01（2026-07-20，harvest 097 dir4）：同色背景把追蹤框輪廓黏掉——綠框貼綠牆＝偵測不到

### 症狀

097 手動重掃的 dir4 畫面裡有一個**肉眼明顯的亮綠色追蹤框**在 `(983, 435)`（D2 格內），
但 `find_tracker` 全畫面回傳的是 `(959, 547)`（角色的臉）。真框附近 ±70px
**連一行 log 都沒有**——它不是排序輸掉，是在 HSV 輪廓階段就出局，形狀確認根本沒跑到。

### 量測

真框被合併進一個橫跨畫面的大輪廓：

```
包住真框的輪廓: bbox=(679,406,493x85) area=14620  (佔全畫面 0.7%)
   area 閘 400~5000 -> 被擋
   bbox 閘 18~80    -> 被擋
```

色域沒問題：框心 HSV `[63, 244, 255]`，綠系範圍 `H 18-78 / S≥80 / V≥50`
（`vision._TRACKER_COLORS[0]`）確實涵蓋。問題出在 `cv2.RETR_EXTERNAL` 把追蹤框
和它身後**同色系、被照亮的綠色牆面**接成同一條輪廓，而 area/bbox 兩個閘是照
「孤立的 18~80px 小框」設的（`vision.py:379-385`），於是整塊被 `continue` 掉。

### 分離信號存在，但現成門檻都不能直接用

| 區域 | S | V | S>200 且 V>200 佔比 |
|---|---|---|---|
| 追蹤框綠芯 | 194 | **222** | 0.502 |
| 黏連的綠牆帶 | 171~216 | **72~76** | 0.000 |
| 一般綠背景 | 242 | **20** | 0.000 |

亮度 V 分得很開（222 vs 75 vs 20），但**兩條看似直覺的改法都已被量測否決**：

1. **加「S>200 且 V>200」的亮芯 mask** → 全畫面通過現行閘的候選 = **0**。
   只留最亮那 ~50% 會把框形打碎，面積掉到 400 以下。
2. **把綠系 V 下限從 50 拉高**（牆帶 V≈72~76，拉到 ~120 可濾掉）→ 會殺暗框。
   同一個框的右下角實測 `V=22`，框自身就有暗部；這是全域門檻，影響所有階級。

### 建議方向（未實作）

加一條**超大輪廓救援**：輪廓爆掉 area/bbox 閘時不要直接 `continue`，改在它的
bbox 內做二次分割（較高 V 的子 mask 重找輪廓，或直接在該 bbox 內跑形狀模板）。
不動全域色域門檻，只在「本來就必然漏掉」的情況多試一次。

**動手前必須先備三側 fixture**，缺一不可：

- (a) 同色黏連的真框（097 dir4 這張）
- (b) 現在就能正常抓到的孤立框（確認救援不改變既有行為）
- (c) 真的該被拒的大色塊（牆面、角色衣裝）——救援不得把它們放進來

### 影響範圍

這條很可能是**「全八方位掃描全空」的一大來源**：這個世界整片是綠的，綠色階級的
框（Exquisite H≈64）貼上任何受光綠面就會消失。不只影響遠端瞄準，也影響一般 sweep。

### 重跑指令

```powershell
uv run python -c "import cv2,glob,os;from miningbot import vision;from miningbot.config import DEFAULT as cfg;tpls={os.path.basename(p):cv2.imread(p,cv2.IMREAD_UNCHANGED) for p in glob.glob('assets/markers/*.png')};f=cv2.imread(r'<snapshots>\20260720_162145_122911600_000102_097_manual_survey_dir4.png');print(vision.find_tracker(f,shape_templates={k:v for k,v in tpls.items() if v is not None and v.ndim==3},shape_threshold=cfg.tracker_shape_threshold,shape_hard_floor=cfg.tracker_shape_hard_floor,shape_scales=cfg.tracker_shape_scales,shape_roi_px=cfg.tracker_shape_roi_px,with_score=True))"
```

預期（未修復時）：回 `(959, 547, 0.61)`，不是 `(983, 435)`。

## D02（2026-07-20，harvest 097 dir4）：角色的臉通過 confirmed 門檻——全畫面兜底可能打到自己

### 症狀

同一張 dir4 幀，`(959, 547)`（角色的臉）形狀分 **edge=0.61**，高於 confirmed
門檻 0.42，被判 `OK` 並成為全畫面最佳命中。

```
shape確認 (959,547) colored=0.72 edge=0.61 ring_ok=False floor=0.30 thr=0.42 -> OK
```

### 為什麼現在才要緊

H056 新增的**全畫面兜底**（`_execute_remote_fire`，ROI 重找全滅後、盲開先驗點之前）
只認 0.42 confirmed 門檻。在角色遮擋的場景，這條路會朝角色的臉開火——
**這是 H056 引入的新風險**，不是既有行為。

代價目前有界（一發 D3 ＋一次 episode），但方向錯誤：兜底的前提是「confirmed
等級比盲開可信」，而這張幀證明 confirmed 等級可以是角色本身。

### 待查

- 角色五官為何拿到 0.61：`best_outline_score` 是多尺度模板比對，臉部輪廓
  （雙眼＋口鼻的閉合結構）可能與某張框模板的外框在小尺度下吻合。先確認是哪張模板
  （逐 `shape_templates` 印分數）與哪個 `shape_scales` 尺度命中。
- 若是小尺度誤命中 → 考慮對 `shape_scales` 設下限，或要求命中尺寸與 bbox 相符。
- 短期可考慮的保守做法：兜底改為「找到也不直接開火，先回報候選圖請人確認」，
  把 H056 的自動開火降級。此改動與 `remote_aim_fullframe_fallback` 開關同層。

### 關聯

D01 與 D02 是同一張幀的一體兩面：**真框進不了候選池，假框（臉）卻拿到 confirmed。**
修 D01 讓真框回到候選池後，D02 的排序問題才會真正浮現——兩條建議一起處理。

## D03（2026-07-20，harvest 097）：近失候選外露閘只看 colored，角色衣裝會洗版

### 症狀

097 giveup 時 Discord 發的 9 個近失候選**全部是角色身上的紅武器與彩虹碎片衣裝**，
沒有一個是真框。使用者只能在垃圾清單裡挑，必然指錯。

### 量測

外露閘是純 `colored_frac > 0.40`（`vision.py:432`）。097 DIR1 那群
`colored` 高達 **0.88~0.90**（飽和紅／彩虹輕鬆過閘），但 `edge` 僅 **0.20~0.34**
（< thr 0.42）且 `ring_ok=False` → 全 hard_rej，卻仍被外露成候選。

### 已修的部分

H056 只修了**重複計數**（`_dedup_rejects`：同層同方位 <60px 合併），
讓一塊衣裝不再佔 3 個名額。**來源未修**——鏡頭卡進角色特寫時清單一樣會被洗版。

### 建議方向（未實作）

外露閘改成 colored **且** edge 雙條件。風險：可能誤殺「薄暗小框」那族
（實測 edge 0.19~0.22，見 `incidents.md` 全方位全空兩型根因），需先備兩側夾 fixture
再動。

## D04（2026-07-20，harvest 097）：同一方位在 sweep 與開火兩個時點構圖差異極大

### 症狀

097 的 dir5 在 sweep（16:20:38）與開火（16:22:30）兩張幀構圖**完全不同**
（正面大頭特寫 vs 背面）。姿態記帳已核對自洽：giveup 回轉 `net=7` → 手動掃 8 次
（≡ 0 mod 8）→ `rot=-3` ≡ dir5，沒有算錯。

### 為什麼要記

衍生風險是**格子座標跨時間不可重現**：使用者在快照上指的格子，開火時可能已經指向
別的東西。回礦側已有同族守門（`incidents.md` H050 的「快照 vs 現場」漂移檢查，
`reentry_remote.zoom_drifted`），**挖礦瞄準側目前沒有任何等價守門**。

### 待查

推測為 camera collision 解算差異（鏡頭卡進角色時，同一 yaw 兩次解出不同機位），
但證據不足以定裁。若成立，H050 那套「快照同格 vs 現場同格比對超標就警告」可以直接
移植到 `_execute_remote_fire` 的對齊後、重找前。

## D05（2026-07-20，harvest 097）：鏡頭卡進角色特寫時，八方位 sweep 整輪全空

### 症狀

097 的 sweep 八個方位全部 `no tracker` → 交人工。畫面顯示鏡頭卡在角色特寫
（camera collision），角色身體塞滿畫面中央，礦區幾乎看不到。

### 為什麼要記

H056 的修正**完全沒有動這一段**——只把「人工介入後仍失手」變成「人工介入會中」，
**不減少交人工的次數**。要真正降低打擾頻率，得處理遮擋本身（偵測到特寫就先退鏡頭／
移動再掃），這是獨立且較大的題目。

與 D01 可能有共同放大效應：遮擋讓可見範圍變小，同色黏連又吃掉剩下的真框。
